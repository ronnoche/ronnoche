Rule of Thumb: Model Data Table

January 24, 2024
Tech

I was building my side-project called "Moneyger", and I was trying to figure out how to model the data. And I got into this decision of whether a concept needs a table or not.
"When do we need to create a table? Or when do we need to create a enum?"

I came up of a solid rule of thumb when designing data models in Rails (or any app): If a business concept needs CRUD, it likely needs a data table.

This principle works well in most cases, especially when you're deciding whether a feature requires a dedicated database table. But like any rule of thumb, there are exceptions and nuances worth understanding.

Why This Rule Works (Most of the Time)

If you need to do any of the following, you probably need a table:

  • Create: Users create instances of something (e.g., goals, transactions).
  • Read: You need to display this concept somewhere (e.g., “Show all bucket targets”).
  • Update: Users need to modify this thing (e.g., adjust a goal amount).
  • Delete: Users may remove or cancel this thing (e.g., remove a funding entry).

When CRUD ≠ Data Table

There are situations where something feels like CRUD but doesn't need a table:

1. Non-Persistent or Computed Concepts

These are values derived from other data, recalculated on the fly:

  • Monthly Savings Progress: Computed from funds vs. targets (No Table).
  • Current Budget Status: Derived from balances and contributions (No Table).
  • Suggested Monthly Contribution: Calculated based on goals (No Table).

2. Configuration-Like Concepts (Fixed Values)

These are options the user selects, but they don’t change over time:

  • Cadence Options: Weekly, Monthly, Yearly (Use Enum).
  • Interval Units: Day, Week, Month, Year (Use Enum).

A Simple Decision Framework

When in doubt, ask these three questions:

  • Will the user create, update, or delete this?
    → Yes = Table / No = Enum, Config, or Calculation
  • Does this need to persist between sessions?
    → Yes = Table / No = Computed on the fly
  • Could this change over time, or is it fixed?
    → Change = Table / Fixed = Enum, Constant

Applying This to Moneyger App (Example)

Business Concept Needs a Table? Reason
Bucket List (Goal’s Name) ✅ Yes Users create, edit, delete goals.
Bucket Target (Savings Goal) ✅ Yes Users define and adjust targets.
Bucket Fund (Assigned Money) ✅ Yes Tracks user contributions.
Cadence (e.g., Weekly, Monthly) ❌ No Enum, fixed set of options.
Current Available Balance ❌ No Derived from account + funds.

Final Rule of Thumb (Refined)

💡 If a business concept involves user-driven creation, editing, or deletion, it likely needs a data table.
If it’s derived, fixed, or calculated, it probably doesn’t.

Use this as a guiding principle in your Rails models or any application architecture.

P.S. Modeling data is a skill you refine over time. Keep asking questions, and you’ll develop better instincts.
